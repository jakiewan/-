# BERT 客服意图分类

参考 `07-shopservice` 的本地 BERT 微调和 softmax 分类方式，保留本项目六类标签：咨询、投诉、售后、订单查询、转人工、闲聊。MiniMax 负责工具参数提取和回答生成，不再执行意图分类。

## 先训练，再启动

`bert-base-chinese` 只有预训练能力，必须先用这六类标注数据微调。shop 的 15 类商品查询模型不能直接使用；分类器会拒绝标签不一致的模型。

在项目根目录执行：

```bash
python3 -m pip install -r backend/requirements.txt
python3 -m backend.scripts.train_intent \
  --base-model checkpoint/intent_classify/bert_v2 \
  --data backend/data/intent_context_v3.csv \
  --output checkpoint/intent_classify/bert_context_v3_new \
  --epochs 8 --learning-rate 1e-5 --context-turns 1 --max-length 256
python3 main.py
```

底座需要是包含权重、配置和词表的本地目录，训练和分类都不自动联网下载模型。当前默认加载 `checkpoint/intent_classify/bert_context_v3_continued/`；上面的命令从已微调的 v2 继续训练，保存到新目录，不自动替换默认模型。模型目录已被 Git 忽略。输出目录非空时训练脚本拒绝覆盖；重新训练请指定新的 `--output`。

启动时默认加载上述模型；如使用其他目录，在根目录 `.env` 设置 `INTENT_MODEL_PATH=/path/to/your/best_model`。模型缺失或标签不匹配时启动失败并提示原因，不使用随机分类头，也不静默切回 LLM。

模型目录内的 `config.json` 保存 `id2label`、`label2id`、`intent_context_turns` 和 `intent_max_length`。推理按模型保存的配置编码输入；旧模型缺少上下文配置时按单句、128 token 处理。`evaluation.json` 记录最优验证轮次、accuracy、macro F1、每类 F1 和混淆矩阵。旧版 `bert_v2/`、`best_model/` 均保留，可通过 `INTENT_MODEL_PATH` 指向相应目录并重启后端回退。

## 数据与评估边界

默认 `backend/data/intent_context_v3.csv` 是人工编写的开发语料，共 1,668 条：1,128 条训练、252 条验证、288 条开发回归。数据按 `dialogue_id` 分组检查，六类数量均衡，包含无历史单句、上下文追问和话题切换；共享同一历史问答的样本不会跨集合。旧版 `intent_v2.csv`、`intent_demo.csv` 保留。

扩展语料覆盖商品参数与排查、售后规则咨询、实际退换修申请、订单/支付/退款/维修进度查询、明确人工请求、闲聊与档案偏好，并补充否定和复合诉求。同一个“确认”“是的，帮我看一下”可根据历史标为不同意图；明确的新诉求必须覆盖旧话题。三个集合没有完全重复的“本轮问题 + 历史”，但仍存在同领域近似表达，指标不能当作真实客服分布上的准确率。

替换数据时使用相同 CSV 格式，并传入 `--data /path/to/intent.csv`：

```csv
text,intent,history,split,dialogue_id,scenario
我要申请退货,售后,,train,conversation-1,standalone
确认办理,售后,"用户：我决定把耳机退回去。
助手：您确认需要申请退货吗？",validation,conversation-2,follow_up
```

`history` 为上一轮完整问答，格式固定为 `用户：…\n助手：…`；没有上一轮时为空。标签只表示本轮诉求，历史不能包含本轮之后的回答。`split` 为 `train`、`validation` 或 `test`；旧数据可以没有测试集。上下文模式要求带历史的样本提供 `dialogue_id`。脚本拒绝空问题、未知标签、重复输入、未覆盖六类的划分和跨集合会话；真实数据还需人工检查近重复。

分类边界：询问排查方法、退换货条件或维修流程归咨询；明确要求办理退换修归售后；查询订单、物流、支付及已提交售后单的进度归订单查询；明确要求真人优先归转人工，但否定人工请求不应触发该类别；天气、姓名和记忆偏好等归闲聊。

当前 v3 输入为 `[CLS] 用户：本轮问题 [SEP] 用户：上一问\n助手：上一答 [SEP]`，最多 256 token。训练与推理共用 `intent_input.py`，优先保留本轮问题，剩余预算保留上一轮用户消息及助手回复的前部。超长本轮问题也会截断，长助手回复尾部的信息可能丢失。

窗口固定为一对历史问答（两条历史消息）加本轮用户消息，共三条。只取紧邻上一轮用户消息及其最终助手文本，忽略工具返回、工具调用规划和系统提示；上一轮没有最终回复时不借用更早的历史。原始消息、完整回答上下文和长期记忆不被裁剪或覆盖。`intent` SSE 事件额外包含 `context_used`，分类说明会显示“参考上一轮问答”。

置信度是未校准的 softmax 分数，低于 0.5 时只显示需确认提示。上下文分类只输出六类意图，不表示已唯一识别商品或订单；多个指代候选、窗口外引用和业务操作授权仍需后续处理。

## v3 验证记录

首个从预训练底座重训的候选，在开发回归中存在单句退化，因此未启用。最终版本从 v2 继续全参数微调 8 轮，学习率 `1e-5`，按验证集 macro F1 选中第 2 轮，验证准确率 99.21%。

前 288 条测试题已用于诊断首个候选，后续仅作为开发回归，最终候选正确率 98.61%。另外预先固定 `intent_context_holdout.csv` 的 126 条新会话验收题，在最终模型选定后首次评分：

| 场景 | v2 | v3 |
| --- | --- | --- |
| 无历史单句（36 条） | 35/36 | 36/36 |
| 上下文追问（54 条） | 20/54 | 53/54 |
| 明确切换话题（36 条） | 35/36 | 36/36 |

新会话总正确率为 125/126（99.21%）。仍有一个低分错例：在“键盘进水、先自行排查”的背景下，“好的，继续”被分为售后，分数约 40.7%。原有 90 条单句回归中 v3 为 88/90，比 v2 的 89/90 多错一条；已知投诉渠道咨询的高分错例仍存在。

真实 HTTP 正常登录独立账号后连续测试 12 条，包含商品指代、物流追问、换货确认、人工确认、人物问答和话题切换，全部分类正确，所有 SSE 正常结束；`context-evaluation.json` 和 `api-results.json` 保存明细。测试使用人工开发语料，不能据此宣称真实客服准确率或普遍覆盖率。

## v2 历史验证记录

2026-10-20 使用相同底座全参数微调 8 轮，按验证集 macro F1 选中第 4 轮。固定的 90 条单句开发测试题上，旧模型准确率为 82.22%，v2 为 98.89%；v2 的 macro F1 为 0.9889，平均预测分数为 99.14%。`comparison.json` 保存同题新旧对照。

正常登录独立测试账号，通过真实 HTTP `/api/chat/stream` 连续发送 12 条问题、使用真实 MiniMax 回复，分类全部正确，分数为 98.63%–99.56%；每次均验证 `start → intent → delta → done`，详情在 `api-results.json`。测试覆盖“我要真人客服帮我处理投诉”，v2 正确识别为转人工，分数约 99.27%。

独立测试仍有一个高分错误：“我不是要投诉只想了解投诉的正规渠道”被误分为投诉，分数约 98.72%。这表明高分并非正确保证，当前尚未进行概率校准；类别仍用于辅助回答，不作为强制业务路由。后续需用真实客服数据补充边界表达和独立评估。

## 意图到查询的衔接

实际聊天路径为：BERT 分类 → 将类别和置信度写入 Agent 状态 → MiniMax 从对话中提取工具参数作为槽位 → 执行已注册工具 → 根据工具结果生成回答。缺少必要参数时追问，不从意图标签推断商品、订单或城市。

例如天气仍归闲聊，但 Agent 可以从“武汉现在天气怎么样”提取 `get_weather(city="武汉")`，查询后再回答。已有记忆、天气工具和 SSE 的事件名称保持不变；`intent` 事件额外带 `confidence`。

当前没有商品图谱、订单接口或知识库数据源，因此尚未实现 shop 的 UIE 实体抽取、MySQL/Milvus 对齐及 Neo4j 商品查询；`workflow.py` 的六节点骨架仍有五个业务占位节点，没有接入聊天接口。此处借鉴的是处理顺序，不代表这些业务功能已经完成。
